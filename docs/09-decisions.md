# 09 架构决策记录（ADR）

格式：每条记录包含背景、决策、后果。状态：`accepted`（v1 生效）、`proposed`（待定）、`superseded`。

---

## ADR-001：使用 pywebview + hpm-gui 风格 UI

**状态**：accepted（2026-11-16）

**背景**：需要一个 Python 桌面应用，界面可快速迭代，且用户明确要求参考 hpm-gui 的导航形式。

**决策**：

- 窗口使用 pywebview；Linux 走 GTK/WebKit2，Windows 走 WebView2。
- 前端不使用 npm/Vite；原生 HTML/CSS/JS + layui。
- 顶栏 + 左侧导航 + 每页独立 `web/pages/<id>/{index.html,page.js,page.css}`；后端页面注册表驱动导航。
- 参考 hpm-gui 的 `definePage` / `showPage` / `get_pages` 模式，但增加 hash 路由与模块参数。

**后果**：

- 优点：无 Node 构建链；Python 与 JS 边界清晰；复用 hpm-gui 已验证的 pywebview 经验。
- 代价：前端组件化能力弱；复杂交互需手写；layui 样式需要定制。
- 风险：WebKitGTK 与 WebView2 的 CSS/JS 差异；需要双平台验证。

## ADR-002：插件与模块统一为 zip 包，主程序内加载 Python

**状态**：accepted

**背景**：用户要求插件和外部模块都是“独立编译”的 zip 包；同时希望开发简单。可选方案：独立进程 RPC、子解释器、in-process import。

**决策**：

- 统一包格式 `.focpkg`（zip），类型 `plugin` / `module` / `bundle`。
- 包内 `backend/` 是 Python 包；加载器用独立命名空间 `freeocs_pkg_<id>` 导入。
- 外部包装到用户数据目录；内置包源码在开发模式直接加载，发布模式加载构建后的 zip。
- 依赖声明在 manifest；安装时经用户确认后 `pip install`。
- v1 不支持运行中热卸载；安装/更新后重启生效。

**后果**：

- 优点：开发/调试简单；能力调用是普通 Python 调用；打包体积小。
- 代价：包可执行任意代码，无沙箱；包崩溃会影响主进程；不能跨语言。
- 缓解：安装警告；只信任来源；异常捕获；未来可加子进程插件。

## ADR-003：能力注册表 + 显式 requires/provides

**状态**：accepted

**背景**：模块不应依赖具体实现；同一能力可能有本地/云端多个实现；用户要求“模块声明需要的能力，插件声明提供的能力”。

**决策**：

- 能力用点分字符串 ID；插件在 manifest 声明 `provides`，运行时 `api.provide`；模块声明 `requires`。
- 框架启动时解析依赖；缺失能力的包标记不可用，不阻塞其他包。
- 同一能力多提供者时，用 `capabilities.<id>` 设置绑定；未指定时自动选择第一个可用提供者。
- 核心能力 `web.bridge`、`android.adb` 由框架提供，不需要插件。
- v1 不解析能力版本约束，只保留 `version` 元数据。

**后果**：

- 优点：模块与实现解耦；切换本地/云端只改设置；新增能力不破坏旧模块。
- 代价：多一层间接；依赖错误要等启动时才发现；需要设置页展示绑定关系。
- 未来：能力版本约束、动态重载、能力权限。

## ADR-004：网页自动化使用 webcat 扩展 + 页面 Agent，不用 Playwright

**状态**：accepted

**背景**：网页应用需要操作已登录的浏览器。候选：Playwright 启动 Chromium、扩展中继、CDP 连接。用户明确选择 webcat，并要求内置 MV3 + Firefox。

**决策**：

- 内置浏览器扩展（Chromium MV3 + Firefox MV3 事件页），后台长轮询本地服务。
- 通用 DOM 操作由 content script 执行；站点适配由模块的页面 Agent 提供。
- 页面 Agent 由本地服务下发，扩展在匹配页面注入；Agent 通过扩展后台代理调用模块 API。
- 不使用 Playwright/无头浏览器；不接管用户浏览器调试端口。

**后果**：

- 优点：复用用户登录态；扩展通用；模块可携带自己的站点脚本。
- 代价：依赖用户安装扩展并保持浏览器打开；MV3 service worker 生命周期、CSP、商店政策有约束；Firefox 临时扩展重启失效。
- 缓解：指南页分步引导；连接状态检测；v1 不承诺商店上架；后续可做签名包。

## ADR-005：本地中继用标准库 http.server，不引入 FastAPI

**状态**：accepted

**背景**：需要本地 HTTP 服务处理扩展长轮询、页面 Agent API、静态资源。参考项目用 FastAPI/Flask，会引入 uvicorn/pydantic 等依赖。

**决策**：

- 使用 `ThreadingHTTPServer` + `BaseHTTPRequestHandler`。
- 只监听 `127.0.0.1`；默认端口 8765，可配置。
- 路由手写，保持小而清晰；长轮询用队列/Event。
- 未来需要 WebSocket/流式时再评估 Starlette。

**后果**：

- 优点：依赖少、打包简单、启动快；行为可控。
- 代价：没有自动校验/OpenAPI；路由与并发需自己保证；大文件上传要手写。
- 缓解：统一 JSON helper、错误码、单元测试；v1 不做大文件上传。

## ADR-006：Android 使用 adb CLI + uiautomator，OCR 兜底

**状态**：accepted

**背景**：参考 aiQuestion 已验证 `uiautomator dump` 的文字/坐标精度；用户要求截图 + OCR 兜底。

**决策**：

- 通过 `adb` 子进程执行命令，不依赖 adbutils/Appium。
- 主路径：`uiautomator dump` → XML → 模块 Reader → 文字 + bounds 中心点。
- 兜底：截图 → `media.ocr` → 文本/坐标；匹配不到坐标则停止。
- 点击带随机偏移；提交/交卷按钮永不点击。
- v1 单设备；API 支持 serial。

**后果**：

- 优点：精确、依赖少、跨平台；Reader 可按 App 扩展。
- 代价：WebView/游戏引擎可能读不到；dump 慢；不同厂商 ROM 有差异；中文输入受限。
- 缓解：OCR 兜底；重试/超时；真机测试矩阵；停止而不是乱点。

## ADR-007：默认只有一套全局文本模型；多模态配置归插件/模块

**状态**：accepted

**背景**：用户明确“默认就一个文本模型，那些多模态的是模块自己的设置”。过早做多配置档会增加 UI 与解析复杂度。

**决策**：

- 全局设置只有一组 OpenAI 兼容文本模型：`base_url`、`api_key`、`model`、温度、超时等。
- TTS/ASR/OCR 等提供者在自己的设置 section 中配置（本地路径、云端 Key、语音名等）。
- 模块可在自己的设置中增加多模态字段（例如 U校园的 TTS 语音覆盖）。
- 不做“按模块切换全局 LLM”的功能；需要时模块可提供自己的模型设置（v1 不实现）。

**后果**：

- 优点：设置页简单；用户心智负担低。
- 代价：不同任务无法用不同文本模型；未来若需要多配置档，需要迁移设置结构（保留 `llm` 作为默认 profile）。
- 缓解：`SettingsStore` 预留 profile 迁移空间，但 v1 不暴露。

## ADR-008：答题 API 只做选择题辅助；复杂题型由模块负责

**状态**：accepted

**背景**：用户指出“传题干 + 选项只适用于选择题，题型会很复杂，框架不可能覆盖那么多题型”。

**决策**：

- 框架提供 `answer.choice`（题干 + 选项 → 选项），作为便捷能力，由 `answer_basic` 插件实现。
- 其他题型（填空、匹配、口语、讨论、多选、连线、排序等）由模块直接调用 `llm.chat`，自己构造提示词与解析。
- 框架不定义“万能答题接口”，也不硬编码题型枚举。

**后果**：

- 优点：框架保持通用；模块可针对站点优化提示词；新增题型不需要改框架。
- 代价：模块之间可能重复实现相似解析；需要模块作者负责质量。
- 缓解：提供 `prompts.py` 模板/工具函数作为示例；后续可抽共享库，但不放进核心契约。

## ADR-009：媒体能力本地优先、可切云端

**状态**：accepted

**背景**：用户要求本地优先、可切云端；隐私与离线可用性重要，但本地模型依赖重。

**决策**：

- ASR：内置 `asr_whisper`（faster-whisper，本地）与 `asr_openai`（云端，可选）。
- OCR：内置 `ocr_rapid`（RapidOCR，本地）；tesseract 作为后备；云端视觉 OCR 后续。
- TTS：内置 `tts_system`（本地系统语音）与 `tts_openai`（OpenAI 兼容云端）。
- 通过能力绑定切换；模块不关心具体实现。
- 重依赖不进入核心安装包；插件声明依赖，安装时确认。

**后果**：

- 优点：离线可用；用户可选择成本/质量；隐私可控。
- 代价：安装体积/模型下载；本地质量参差；需要清晰的错误提示与配置引导。
- 缓解：设置页显示“可用/未安装/模型缺失”；首次使用下载；云端作为回退。

## ADR-010：绝不自动提交/交卷/发布

**状态**：accepted（硬约束）

**背景**：参考项目 U校园 会点击“提交/确定”，aiQuestion 已停止在提交页。用户明确要求只填答案。

**决策**：

- 所有模块硬编码安全模式：只填答案、只点导航/媒体控制；不点提交、交卷、发布、确认提交、评分提交。
- 检测到提交页/弹窗 → 状态 `waiting`，提示“等待手动提交”，停止自动化。
- 讨论区只填内容，不点“发布”。
- 配音/角色扮演等“录音即提交”的题型，v1 停止并提示手动完成。
- 测试用例必须覆盖所有提交按钮路径。

**后果**：

- 优点：避免不可逆误操作；降低账号风险；符合用户预期。
- 代价：不能实现“全自动完成课程”；部分题型需要人工；流程会在提交页停下。
- 未来：即使用户要求，也不默认开放；如开放需显式高风险开关与二次确认（v1 不做）。

## ADR-011：U校园采用“页面 Agent + Python 大脑”移植

**状态**：accepted

**背景**：参考油猴脚本 2541 行，DOM 选择器/Shadow DOM/iframe/目录状态机复杂；全部重写成 Python + webcat 通用 DOM 调用成本高、回归风险大。

**决策**：

- 保留页面侧逻辑，移植为模块的 `web/page-agent.js`（含轻量控制面板、无 GM API）。
- Python 模块负责模型、ASR/TTS、提示词/解析、会话状态、租约、日志、设置。
- 页面 Agent 通过 `__freeocs` 桥调用模块端点；扩展只做注入与传输。
- 移除所有提交/发布点击，增加 `waiting` 状态。

**后果**：

- 优点：移植风险低；DOM 逻辑靠近页面；Python 侧可复用框架能力。
- 代价：模块包含较多 JS；页面脚本调试依赖浏览器；页面 CSP 可能阻止本地 bundle 注入。
- 缓解：保留原脚本作为参考；逐函数移植；fixture + 手动回归；必要时回退 `scripting.executeScript`。

## ADR-012：设置以 JSON 明文存储，权限 0600，v1 不接 keyring

**状态**：accepted

**背景**：参考项目使用 `.env`/config.json；用户要求设置页统一配置。keyring 在 Linux 桌面/打包环境下不稳定。

**决策**：

- 配置存 `~/.config/FreeOCS/settings.json`（Windows `%APPDATA%`）。
- 文件权限 `0600`（Windows 依赖用户目录 ACL）。
- API Key 明文存储；UI 不回显；日志脱敏。
- 提供“打开配置目录”；文档明确风险。
- 后续可加 keyring/加密，保持字段兼容。

**后果**：

- 优点：实现简单、可移植、易备份/排查。
- 代价：本机其他进程/备份可能读到密钥；不适合共享电脑。
- 缓解：权限、脱敏、文档警告；未来加密迁移。

## ADR-013：Python 3.12 + uv；打包以 onedir 为主

**状态**：accepted

**背景**：系统 Python 3.14 对 faster-whisper/torch/onnxruntime 兼容性差；用户最终要单文件/安装包。

**决策**：

- 项目固定 Python 3.12，用 uv 管理解释器与虚拟环境。
- 开发用 `uv run`；CI 用同样版本。
- 发布优先 PyInstaller **onedir** + tar.gz/zip/安装器；onefile 作为可选实验。
- 模型不打进安装包；运行时下载到数据目录。

**后果**：

- 优点：依赖可复现；打包调试容易；更新包/扩展方便。
- 代价：onedir 文件多；onefile 启动慢/易误报；用户需单独下载模型。
- 缓解：安装器包装；首启引导；模型下载进度/校验。

## ADR-014：浏览器扩展 MV3 + Firefox，v1 不承诺商店上架

**状态**：accepted

**背景**：Chrome 已不支持 MV2；Firefox 支持 MV3；用户要求两者兼容。扩展需要 `<all_urls>` 与页面注入，商店审核较难。

**决策**：

- Chromium 使用 MV3 service worker；Firefox 使用 MV3 事件页（`background.scripts`）。
- 共享 `shared/` 源码，两个 manifest 分别构建。
- v1 以“加载已解压/临时载入”为主；不提交商店。
- 扩展只连接 `127.0.0.1`；不收集数据。

**后果**：

- 优点：现代浏览器可用；代码复用；安装可控。
- 代价：Firefox 重启失效；Chrome 首次安装步骤多；商店政策风险。
- 未来：签名 XPI、Chrome Web Store 上架、自动更新。

## ADR-015：本地 API 使用“扩展头 + 页面 Origin 白名单”，v1 不加共享 token

**状态**：accepted

**背景**：本地 LLM Key 不能被任意网页滥用；但扩展安装/配对流程越简单越好。参考项目无鉴权。

**决策**：

- 只监听回环地址。
- `/api/module/*` 要求 `X-FreeOCS-Client: browser-bridge`（页面自定义头会触发预检，服务端拒绝）。
- 校验 `X-FreeOCS-Page-URL` 的 host 是否匹配模块 `web.allowed_hosts`。
- `/extension/*` 同样要求扩展头；不校验扩展 ID（v1）。
- 不引入共享 token；页面脚本无法访问 `__freeocs` 桥。
- v1 的威胁模型：本机进程可信，浏览器页面不可信。

**后果**：

- 优点：安装零配对；实现简单；能阻止网页直接盗用 LLM。
- 代价：本机恶意进程仍可调用；扩展 ID 未校验；未来需要 token/配对。
- 缓解：文档说明；后续加 `bridge_token` + 扩展设置页配对。

## ADR-016：安装/更新后重启生效，不做热卸载

**状态**：accepted

**背景**：Python 模块一旦 import 就难以安全卸载；运行中替换代码/对象容易导致状态不一致。

**决策**：

- 安装、更新、卸载、启用/禁用包后，提示用户重启应用。
- 运行中的模块先停止；不尝试卸载 `sys.modules`。
- 设置变更可即时生效（能安全刷新的提供者实现 `on_settings_changed`）。

**后果**：

- 优点：行为可预测；避免隐蔽 bug。
- 代价：用户体验略差；开发迭代需重启。
- 缓解：开发模式 `--dev` 自动重启脚本（后续）；UI 明确提示。

## ADR-017：文档先行，文档与代码同仓库

**状态**：accepted

**背景**：项目跨度大、模块/插件契约多；口头约定容易漂移。

**决策**：

- `docs/` 是设计基线；manifest/SDK/协议变更先改文档。
- 每个模块包内自带 README（面向使用者）。
- 架构变更记录 ADR；实现与文档不一致时，先修正文档或代码，不能长期偏离。

**后果**：

- 优点：多人/多 agent 协作有共同契约；减少返工。
- 代价：维护文档成本；需要纪律。
- 缓解：文档评审；把关键契约写成测试。
